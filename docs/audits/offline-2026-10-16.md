# Offline audit: student and family pages (2026-10-16)

Question: which student and family pages work offline, and why or why not.

Evidence labels used on every claim:

- MEASURED: observed in headless Chromium (Playwright) against a local static server.
- READ-FROM-CODE: read from source or from the live `sw.js` bytes; not exercised in a browser.
- LIVE-GET: read-only HTTP GET of a public file on https://eduwonderlab.com (no browsing, no beacons).
- NOT MEASURED: could not be measured; reason given.

Branch state: worktree `/Users/joelneft/wt-award-gold` at origin/main aa873132f0 plus other agents' edits. Nothing in the repo was edited except this file.

## 1. Headline

1. The lesson launchers (`/lessons/<u>-<l>/`), which are the main student surface, no longer register any service worker. `lessons/sw.js` is shipped and cached-name-stamped but is dead code (READ-FROM-CODE + LIVE-GET + `node tools/inject-offline-sw.mjs --check` reports all 64 launchers INVALID). The registration block was removed from every launcher by commit c35e102ff0 (2026-07-21, "update 222 HTML lesson shells"), and the injector was never re-run. Only `practice-arcade` still carries its block.
2. Only four things register their own offline worker today: the Curriculum Hub and Units page (root `/sw.js`), Math Intervention, Practice Arcade, Monster Math Academy (plus Math Workbench, but only on https, and Family Connections, which unregisters itself). Everything else is online-only unless the visitor first loaded `/curriculum/` or `/curriculum/units/` (which registers the origin-wide root worker).
3. Family homework (`/lessons/<id>/homework.html`, `/families/`, `/math/family/`) has no worker of its own. A family that opens a shared link directly gets no offline support at all (MEASURED: every row in table A fails offline). A student who came through the hub first gets same-URL offline support from the root worker (MEASURED, table B), but never a neutral offline fallback: any uncached page returns the teacher Curriculum Hub (MEASURED).
4. Save/Resume is genuinely local-first and works offline on every page where it loads (MEASURED). Cloud sync is opt-in and no page in the repo enables it, so "cloud save-code writes offline" is a dormant path. Game/practice score uploads are lost when offline and cannot be retried the same day (MEASURED).
5. No worker caches `/api/*` responses (READ-FROM-CODE for every worker; MEASURED for root, intervention, arcade, mma: `/api/*` is never served from a cache entry). Cache names collide and evict each other (MEASURED on source names, LIVE-GET on production names).

## 2. How it was measured (and what could not be)

Server: `/private/tmp/claude-501/.../scratchpad/f8/server.mjs` on port 8711 (Node, not `python3 -m http.server`). Deviation from the brief, with the reason: python's server cannot serve `/sw.js` (the root worker lives in `public/sw.js` and Vite copies `public/` onto the site root), and it sends no Cache-Control so Chromium's heuristic cache could mask real offline failures. The Node server overlays `public/` on the root, redirects directory URLs like Pages, answers `/api/*` with a 404 JSON, and sends `Cache-Control: public, max-age=0, must-revalidate` (the Pages default). It was killed after the run. Scripts: `measure.mjs`, `measure2.mjs`, `measure3.mjs`, `measure4.mjs`, `measure5.mjs` in the same scratchpad directory (outside the repo); to re-run against a built `dist/`, change `BASE` and serve `dist/`.

Per URL the harness did: fresh browser context, `goto`, wait for any registration and `serviceWorker.ready`, wait 3.5 s, then `context.setOffline(true)`, `page.reload()` (same URL), and `goto` to a second URL never visited in that context (new URL). Control check: from an SW-controlled page, `fetch("/__not_cached_control__")` rejected with "Failed to fetch" in every row, so offline emulation does apply to worker network fetches. Three scenarios:

- A. Fresh visitor, visited once. Also run as "visited twice" (reload online, which is the first time a worker controlling the page can cache its subresources). Table A.
- B. Hub-primed: load `/curriculum/units/` first (registers root worker), then the target twice, then offline. This is what a student who came from the hub looks like. Table B.
- C. Forced registration: `navigator.serviceWorker.register` called by the harness on pages whose own registration is missing (lesson pages) or https-only (Math Workbench). Simulates "if the registration were restored". Table C.

Not measurable on a static server (no build run, per the brief), so the status of these is NOT MEASURED:

- Lesson launchers `/lessons/<id>/` and anything rendered by `lesson.js`: it imports the bare specifier `@engine/...` and `config.json` and needs the Vite `dist/` build. Online load shows the engine's own "This lesson is having trouble loading" panel (238 characters), so no render assertion is possible. Only the HTML shell and the worker mechanics were exercised.
- `/assets/homework-lesson-models.js` (the Family Math Studio route and the interactive model) is a Vite output at a fixed URL and returns 404 here. Quick and Learn and Practice sections are static HTML and were measured; the Studio default route's interactive model was not.
- Every page that loads `web-vitals` through the bundled `nt-web-vitals.js` logs `Failed to resolve module specifier "web-vitals"` online (source-only artifact, dist bundles it). Not an offline defect; excluded from the failure counts below.
- Cloudflare `_redirects`, `_headers`, `_middleware.js` (teacher gate, canonical host, redirect fallback) and Functions did not run. `/api/*` returns 404 on this server; those 404s are counted as "api-404 (server)" and never as offline failures. Offline `/api/*` calls fail with `ERR_INTERNET_DISCONNECTED`.
- Cross-origin resources (GeoGebra, Google Fonts) cannot be loaded offline here. The Workbench GeoGebra cache-first branch is NOT MEASURED.
- A real Chromebook / iPad / Safari: only Chromium was used.

| Limits of that queue (READ-FROM-CODE)                                                                                                            | `_remotePending` is a plain in-memory flag, not a durable queue: it is lost if the tab closes while offline, and replay only fires if a new save occurs or the `online` event fires in the same page session. Only the `cloudflare` adapter replays; the Apps Script adapter does not. No retry other than the next `online` event.              |
| Resume code on another device while offline                                                                                                      | Cannot work: lookup is local first, then the backend; with localStorage-only default there is no cross-device record at all (READ-FROM-CODE, documented in `SAVE_RESUME_SYSTEM.md`).                                                                                                                                                             |
| Score upload offline (`EduPulse.record` on `/math/games/u1-factor-frenzy/`)                                                                      | `POST /api/scores` fails with `ERR_INTERNET_DISCONNECTED`; a `nt-score-sent:*` key was already written. After reconnect, repeating the same payload makes NO request (dedupe key). The score is lost. READ-FROM-CODE for cause: `assets/edupulse-bridge.js:528-529` calls `markSent()` before `record()`, and the `.catch` swallows the failure. |
| Usage beacon `assets/nt-usage.js` offline                                                                                                        | Fails silently by design (its header: failed beacon is dropped). On Intervention it also fails to load offline because `/assets/nt-usage.js` is outside that worker's managed prefixes.                                                                                                                                                          |
