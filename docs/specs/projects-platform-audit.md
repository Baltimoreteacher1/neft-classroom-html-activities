## Studio feedback (math.mjs)

All 30 missions run `model(project, values)` and return 6 deterministic checks
with finite answers, a decision string and a worked example. No placeholders.
Logic is per FAMILY (12 engines), with per-mission tuning only for `unit-3-b`,
`unit-9-b`, `unit-10-b` and the three context designs each mission carries.
Gaps: feedback is a right/wrong check with a hint and reason, not a per-step
diagnostic; the twelve engines are shared by 2-5 missions each (`division` x4,
`statistics` x5, `solids` x4), so sibling versions give near-identical feedback.

## Count discrepancies and causes

1. Index pages said "30 missions" as a typed literal in `tools/generate-project-studio.mjs`
   (not in `npm run build`, run by hand). Now derived from the registry; output
   is byte-identical today.
2. Portfolio header and meta said "12 project sets, 27 projects" (correct), but its
   static tiles said "11" and "0 / 23" until JS ran. Fixed to 12 and 0 / 27;
   `validate:projects-registry` now pins all four numbers.
3. Hub footer "10 unit projects" (inside "214 pathways") is `endOfUnitCount` in
   `data/curriculum-launch-manifest.json`: it loops units 1-10 and tests for
   `math/unit-N/projects/index.html`, so it counts the legacy folders 1-10, skips
   the `pre-unit` and `statistics` hubs, and titles `/math/unit-1/projects/` "Unit 1
   Culminating Project" though that content is Unit 6. NOT changed (hub footer and
   launch manifest belong to the curriculum workstream); the registry-derived
   equivalents are 12 sets, 27 pages, 30 missions. Which one the footer should say
   is a decision for Joel.
4. `tools/lib/project-units.mjs` says `math/unit-2/projects` mirrors `statistics`
   byte for byte; they differ (12 diff lines after normalising the folder name).
5. Studio `UNIT_NAMES` ("Math Is Discovery", "Ratios & Rates", "Math Is Synthesis"...)
   disagree with `data/curriculum-unit-identities.json` ("Math Is Mine", "Ratio City",
   "Math Is Everywhere"...). The Pre-Unit hub prints "Pre-Unit · Pre-Unit · Division".
6. `assets/project-readiness-pathways.js` keys (`world-architect`, `cartesian-odyssey`,
   `ratio-lab`, `netfold-3d`, `sports-analytics`) match no registry id except
   `world-architect`; it is loaded only by the hub, which this stage does not touch.

## Hazard found (fixed in Stage 2)

`node tools/generate-project-studio.mjs` used to rewrite `curriculum/units/index.html` and, against
the formatted file, moved `</details>` tags. The generator no longer reads or writes that page (the
Project Studio unit links already committed there stay as they are; the file belongs to the
curriculum hub). `validate:projects-registry` now reruns the generator in a throwaway copy of every
file it can write and fails if any committed file would change, so a rerun on a clean tree is a
no-op. The two galleries are generated from the registry by `tools/lib/projects-gallery.mjs`.

## Gaps against the target

- No per-project workspace: legacy pages are 50-175 KB single-file wizards;
  Studio is a separate model-and-report shell. Two save formats, two rubric forms.
- No shared feedback engine across both: Studio's `math.mjs` and the legacy pages'
  `projects-check` (config-driven) never meet.
- (Closed in Stage 3A) A Studio mission now writes `nt-project-complete:v1:<id>` on explicit
  completion and the portfolio reads it; certificates need a valid record.
- No registry-driven navigation: the portfolio table, hub cards, SCORM catalog and
  `PROJECTS` are four lists kept in step by hand. The registry is the first place
  they can be compared; this stage did not make them consume it.

6. **Name/count cleanup.** Align `UNIT_NAMES` to unit identities, fix the Pre-Unit
   double prefix, and propose the hub-footer wording (needs the curriculum session).
